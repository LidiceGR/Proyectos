# Capstone CMU — SQL AST Parsers (v0.1)

This package adds deterministic T-SQL syntactic parsing to the **existing** `Proyectos` repository. It does **not** replace or modify `source_extractor`. It is designed to consume the `sources_manifest.json` contract from the preceding Source Collector version; verify the schema against any locally adapted extractor before integration.

## Purpose

The parser reads **only the SQL files listed in the source manifest**, uses SQLFluff with the `tsql` dialect, and produces one JSON syntactic segment tree per SQL file. Catalog `.json` files and table metadata `.json` files are not parsed as SQL. No database queries, LLM calls, RAG retrieval, or business-rule inference happen here.

SQLFluff produces a **syntactic segment tree**, not a complete semantic representation of T-SQL and not a Microsoft ScriptDOM AST. Unsupported T-SQL constructs may be reported as partially parsed. These reports must not be interpreted as evidence that a database object does not exist.

## Python API and FastMCP readiness

```python
from sql_ast_parsers import parse_sql_sources


def report_event(event: dict) -> None:
    print(event)


result = parse_sql_sources(
    "workspace/run_001/sources_manifest.json",
    "workspace/run_001/ast_files",
    max_files=1,
    on_event=report_event,
)
print(result["summary"])
```

The callback receives structured progress events such as `sql_parsed` and `ast_completed`. An MCP adapter may forward them as logs, but this package deliberately has no MCP dependency.

## Output contract

Each `<source>.sql.ast.json` contains:

- `source_file`: the relative path from the source collector manifest.
- `source_type`, `source_objects`: provenance from the collector.
- `parser`, `tree_type`, `status`: parser name and status (`ok`, `partial`, `error`).
- `tree`: recursive SQLFluff segment tree with English keys (`type`, `children`, `text`, `line`, `column`).
- `parse_errors` and `unparsed_regions`: unsupported or invalid syntax evidence.

`ast_files/ast_manifest.json` lists the source-to-AST mapping, counts, parser version, and any error state. The following stage (`inventory_builder`) should use **this AST manifest**, not scan unrelated files.

The older Spanish `generar_inventario_relaciones.py` uses `tipo`, `hijos`, `texto`, etc., and is **not yet compatible** with the new AST JSON keys. It must be adapted in a later step; do not feed these AST files to the older generator unchanged.

## Known integration constraint

The public GitHub repository's root folders were visible, but its updated `source_extractor` implementation could not be retrieved in this session. The parser therefore follows the **previously agreed source manifest schema**, including `files[].relative_path`, `file_type`, `objects`, `sha256`, and `suggested_processors`. If the local extractor uses different field names, the correct action is to adjust a small manifest adapter after inspecting a real `sources_manifest.json`, rather than silently guessing or changing the extractor.
