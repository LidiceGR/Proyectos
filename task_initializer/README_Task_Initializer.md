# Task Initializer — Capstone (v0.1)

## Purpose

`task_initializer` creates **investigation tasks, not business rules**. It consumes the structural SQL metadata already produced by `inventory_builder` and identifies logical fragments that a future research agent may need to interpret.

This component is deterministic. It never calls an LLM, queries a database, consults a catalog, or assumes the business meaning of a SQL expression. The future research agent will decide whether each fragment represents a business rule, technical logic, or an inconclusive finding, and which additional tools or evidence it needs.

## Inputs and output

Inputs:

- `metadata/inventory.json`: objects, operations, effects, WHERE conditions, and surrounding IF conditions.
- `metadata/relationships.json`: references to related objects, including targets whose definitions are not in the current inventory.
- `ast_files/`: SQLFluff AST JSON files referenced by each inventoried SQL object.

Output: `research/research_tasks.json`. Every task contains a stable `task_id`, generic `task_type`, pending status, object identity, structured SQL fragment when available, original SQL text reconstructed from its AST node, condition context, related object references, and source/AST locations.

**Catalog values are intentionally not copied into tasks.** They remain in `metadata/catalogs.json` for retrieval by the research agent when it needs them. The initializer does not attempt to resolve codes such as `OperationType = 2`.

## Selection criteria

| SQL structure | Initial task selection |
|---|---|
| `INSERT`, `UPDATE`, `DELETE`, `MERGE` | One task per extracted DML operation, including its IF and WHERE contexts |
| `THROW`, `RAISERROR` | One task per extracted error/validation statement, including surrounding IF context |
| `RETURN` | Only when the inventory records a surrounding IF condition |
| `SELECT` | Only when the inventory records both surrounding IF context and variable assignments |
| `SELECT` without qualifying assignment | Context only; no separate task |
| `TRANSACTION`, commit, rollback | Context only; no separate task |
| Object with no qualifying operation | One generic `inspect_sql_object` task, preventing silent omission |

These rules select **technical structures**, not business semantics. Some selected fragments may be purely technical; their classification is deferred to the research agent. Later versions may refine grouping for nested branches, DML side effects, dynamic SQL, and complex expressions.

## Run one example (PowerShell)

From the project root (`D:\Proyectos\CMUAgent\proyectos`):

```powershell
& "D:\devenv\Anaconda32024.02\Scripts\conda.exe" run --no-capture-output -n cmu-llm python -m task_initializer --inventory workspace\run_001\metadata\inventory.json --relationships workspace\run_001\metadata\relationships.json --ast-directory workspace\run_001\ast_files --destination workspace\run_001\research
```

Expected summary using the provided `run_001` sample:

```text
Summary: {'total_tasks': 3, 'objects_examined': 3, 'by_operation': {'INSERT': 1, 'THROW': 1, 'UPDATE': 1}}
```

To test the second provided workspace, change `run_001` to `run_002` throughout the command. Its expected summary is 5 tasks: two `UPDATE`, two guarded `RETURN`, and one guarded variable-assignment `SELECT`.

An existing `research_tasks.json` is **never overwritten by default**, to protect future agent progress. For an intentional fresh initial queue, remove or archive the old file, or pass `--overwrite`. **Do not use `--overwrite` after a research agent starts updating statuses.**

## Future agent and MCP integration

The main Python function is:

```python
initialize_tasks(
    inventory_file,
    relationships_file,
    ast_directory,
    destination,
    on_event=None,
    overwrite=False,
)
```

`on_event` emits synchronous `task_created` and `tasks_initialized` dictionaries. An MCP wrapper can forward these as log messages without changing the deterministic implementation.

The future research agent will pick a pending task, load its evidence and context, produce an interpretation or request further information, and potentially create **new** dependent research tasks. That decision-making does not belong in `task_initializer`.

## Current limitations

- The initializer trusts operation extraction performed by `inventory_builder`; missing or incorrectly grouped SQL operations cannot be repaired at this stage.
- The AST must have `status = "ok"` and a matching `source_file`, and each selected operation must be matched to an AST node at the same source line. Invalid or missing evidence fails visibly rather than generating a misleading task.
- AST SQL text covers the operation itself. Outer IF context is supplied separately in `fragment.condition_context`.
- `related_objects[].definition_in_inventory = false` means a definition was absent **from the provided inventory**, not necessarily absent from the actual database.
- SQL Server `inserted` and `deleted` references are explicitly marked as pseudo-tables when encountered as relationships.
- This version does not split one complex operation into multiple finer-grained tasks and does not group multiple different operations into a single investigation. That can be considered after agent evaluation.
